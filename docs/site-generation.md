# Documentation site generation

A browsable site (MkDocs + Material theme) generated directly from each algorithm's
`metadata.yaml`, optional hand-written `EXPLANATION.md`, and optional `demo()` function —
not a separate, hand-maintained set of docs that can drift from the code.

## Why two stages

Generating a demo means actually *running* an algorithm's real code — which needs that
algorithm's SDK installed (Qiskit, Cirq, ...). Rendering the site into Markdown/HTML needs none
of that — just the pre-computed results. Mixing these into one step would mean every docs build
needs every SDK installed simultaneously, reintroducing the exact multi-SDK dependency problem
`docs/testing.md` already solved for tests. So the build is two separate tox environments:

1. **Per-framework demo generation** (`tox -e qiskit-docs`, and a `<framework>-docs` env for each
   SDK added alongside its test env — see `tox.ini`). Runs `scripts/generate_demo_outputs.py
   --framework <name>`, which finds every algorithm whose `metadata.yaml` lists that framework,
   imports its implementation (same `importlib`-by-path pattern as tests, to avoid basename
   collisions), calls `demo()` if it has one, and caches the JSON result under
   `website/demo_cache/<algo-id>.json`. An algorithm with no `demo()` yet is skipped, not failed.
2. **Framework-agnostic rendering** (`tox -e docs`). Runs `scripts/render_docs.py`, which reads
   every algorithm's `metadata.yaml` (always present), `EXPLANATION.md` (optional — renders a
   placeholder note if absent), and cached demo JSON (optional — same placeholder treatment),
   and renders each through `website/templates/algorithm.md.j2` into `website/build/`. Then
   `mkdocs build` turns that into the final static site at `website/site/`. Neither step needs
   any quantum SDK.

```bash
tox -e qiskit-docs   # generate demo output for all Qiskit algorithms
tox -e docs          # render pages + build the static site into website/site/
```

Nothing under `website/build/`, `website/demo_cache/`, or `website/site/` is committed — all of
it is fully derived from source (`metadata.yaml`, `EXPLANATION.md`, `qiskit_impl.py`) and
regenerated on every build. Only `website/templates/` (hand-written Jinja2) and this repo's own
`mkdocs.yml`/`requirements-docs.txt` are checked in.

## Avoiding duplication

`metadata.yaml` stays the single source of truth for structured facts (complexity, speedup,
limitations, references) — that's what the planned AI recommendation layer greps, and what the
site's "at a glance" fact box is templated from. `EXPLANATION.md` holds hand-written narrative
*only* — intuition, worked examples, pedagogy that doesn't exist as a structured field anywhere.
Nothing should be typed in both places: if you're restating a metadata field in prose, that's a
sign it belongs in `metadata.yaml`, not `EXPLANATION.md`.

## Conventions for a new algorithm

- `EXPLANATION.md` is optional but encouraged — plain Markdown, no front matter, rendered
  verbatim into the page between the fact box and the demo section.
- `demo()` is optional but encouraged — add it to the implementation file (e.g.
  `qiskit_impl.py`) alongside the algorithm's other functions. Contract: a zero-argument function
  returning a JSON-serializable dict with `description` (str), `parameters` (dict of inputs used),
  and `result` (dict of outputs — a `counts` key renders as a table automatically; everything
  else renders as a bullet list). See
  `algorithms/oracular/grovers-algorithm/qiskit_impl.py`'s `demo()` for the reference example.
- Don't hand-write a demo's expected output anywhere — it's generated by actually running the
  code at build time specifically so it can never silently drift from what the implementation
  really does.
- Add a test that calls `demo()` directly and asserts the shape of what it returns (see
  `test_demo_returns_expected_shape` in Grover's test file). Nothing else exercises `demo()` — a
  renamed function it depends on would otherwise break silently, since it's not part of the
  algorithm's actual correctness tests.

## Wired into the pre-commit hook

`scripts/run_changed_algorithm_tests.py` doesn't just run tests — for each changed algorithm
directory, after that framework's tests pass, it regenerates *just those directories'* demo cache
entries (`tox -e <framework>-docs -- <changed dirs>`), then — if everything so far succeeded —
re-renders and rebuilds the entire site (`tox -e docs`). A commit can't land with passing tests
but a broken template or a `demo()` that produces something the renderer chokes on.

This is also the whole caching strategy, and it's intentionally not fancy: `website/demo_cache/`
is gitignored but persists on disk across commits in a given working tree. Regeneration is scoped
to only the directories a commit actually touched, so an unrelated change leaves every other
algorithm's cached demo output untouched rather than recomputing it. Rendering (Stage 2) always
processes every algorithm — that's fine, since it's pure templating with no simulation, cheap even
at a few thousand pages, and the index page needs to see the whole corpus anyway.

A test failure short-circuits before any of this runs (no point caching a demo for code that just
failed its own tests), and a failure in demo generation or site rendering fails the commit exactly
like a test failure would.

## Running locally

```bash
pip install -r requirements-dev.txt
tox -e qiskit-docs   # or whichever framework(s) you've touched
tox -e docs
# open website/site/index.html, or:
pip install -r requirements-docs.txt && mkdocs serve
```
